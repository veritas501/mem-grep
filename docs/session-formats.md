# Session formats

What mem-grep knows about each agent's session logs, and where it comes from. Rule: formats are taken from the agent's source code (or, for closed-source agents, from real files), never guessed from documentation. Test fixtures are generated by the agent itself — never hand-written, never copied from a real session (real sessions contain secrets).

| Agent | Adapter | Status | Source of truth |
|---|---|---|---|
| omp / pi | `internal/sources/omp.go` | Complete, tested on fixtures generated by omp | `@oh-my-pi/pi-coding-agent` 18.13.2, `src/session/session-entries.ts` |
| Codex | `internal/sources/codex.go` | Skeleton; filtering rules unit-tested, no fixture | `openai/codex` @26ad281 (`codex-rs`) |
| Claude Code | `internal/sources/claude.go` | Skeleton, no fixture; wrappers, interrupts and subagent layout checked against real 2.x transcripts (2026-10-30) | Closed source; real 2.x transcripts |

Open TODOs are listed in each adapter's file header.

## omp / pi

**Files.** `~/.omp/agent/sessions/<encoded cwd>/<timestamp>_<uuid>.jsonl` (`PI_CODING_AGENT_DIR` overrides the agent directory; pi uses `~/.pi/agent/sessions`). The cwd encoding is `-<home-relative path with / → ->` under home, `-tmp-…` for temp directories, `--<path>--` in old versions. The project is the header's `cwd`; never reverse the directory name.

- Subagents: `<timestamp>_<uuid>/<AgentName>.jsonl` — a directory named after the parent session; each file is a complete session with its own header.
- Advisor runs: `__advisor.<n>.jsonl` in the same directory (ignored by default, `MG_ADVISOR=1` includes them).

**Records.**

- The first line *may* be a fixed-width title slot: `{"type":"title","v":1,"title":…,"pad":"   "}`. Then the header: `{"type":"session","version":3,"id","timestamp","cwd",…}`. Titles can change later via `title_change`.
- Entries have `id` (8 hex characters), `parentId` and an ISO `timestamp`, forming a tree. Files are append-only, so file order is chronological. Version 1 files have no ids; the adapter chains their entries linearly.
- The leaf is usually the last entry, but an entry carrying `activeLeafId` was written off the current branch (a late usage record, a background bash result): it restores the leaf rather than moving it. A branch shows up as an entry whose `parentId` is not the current leaf; a root entry (`parentId: null`) after others is a context reset.
- Entry types: `message`, `model_usage`, `thinking_level_change`, `model_change`, `service_tier_change`, `compaction`, `branch_summary`, `custom`, `custom_message`, `label`, `title_change`, `ttsr_injection`, `session_init` (subagent `task` and `agent`), `mode_change`, `credential_pin`, `reset_boundary` (`/clear`).
- Message roles: `user`; `assistant` (blocks `text` / `thinking` / `toolCall{id,name,arguments}`; `stopReason` includes `aborted` and `error`); `toolResult{toolCallId,toolName,content,isError}`; `bashExecution{command,output,exitCode}` and `pythonExecution{code,output,exitCode}` (commands the user ran); `system`, `developer`, `custom`, `hookMessage`.

**Rendering.** Kept: user messages, agent text, tool calls with key arguments, results (failures in full, shell output as a tail), user shell commands, subagent tasks, branch summaries. Marked: branch rewinds, context resets, `/clear`, interruptions, assistant errors. Dropped: thinking, system / developer / custom messages, compaction.

**Regenerating fixtures** after an omp upgrade: see the header of `test/fixtures/gen-fixtures.ts` (it drives omp's own `SessionManager`); then update the Go tests that assert entry ids and counts.

## Codex

**Files.** `$CODEX_HOME` (default `~/.codex`): `sessions/YYYY/MM/DD/rollout-<YYYY-MM-DDTHH-MM-SS>-<thread_id>[_<rollout_id>].jsonl` and `archived_sessions/`. The `_<rollout_id>` suffix appears on reverted threads, so one thread can have several rollout files.

**Compression.** A background job compresses rollouts older than 7 days to `.jsonl.zst` and decompresses them on resume (`codex-rs/rollout/src/compression.rs`; feature `LocalThreadStoreCompression`, under development and off by default). mg reads zstd (detected by magic number) and keys the session by the plain `.jsonl` path; offsets refer to decompressed bytes.

**Lines** (`codex-rs/history/src/lib.rs` `RolloutLine`, `rollout_payload.rs`): `{"timestamp", "ordinal"?, "type", "payload"}` with `type` in snake_case: `session_meta` (always first), `response_item`, `event_msg`, `turn_context`, `compacted`, `inter_agent_communication`, `token_usage_record`, `world_state`, `retained_context`, `dynamic_tools_updated`, ….

**`session_meta`:** `id` (thread), `session_id` (root thread), `timestamp`, `cwd`, `source`, `thread_source`, `forked_from_id`, `parent_thread_id`, `agent_nickname` / `agent_role` / `agent_path`, `history_mode` (`legacy` / `paginated`; non-ephemeral `codex exec` uses paginated), `history_base` (this thread continues another rollout's prefix up to `end_byte_offset`), `subagent_history_start_ordinal` (earlier records are context inherited from the parent), `base_instructions`, `git`.

`source` is a lowercase externally tagged enum: `"cli"`, `"vscode"`, `"exec"`, `"mcp"`, `"unknown"`, `{"custom": "atlas"}`, `{"subagent": …}`, `{"internal": …}`; missing means `vscode`. `thread_source` is `user`, `subagent`, `guardian_review`, `memory_consolidation` or a feature name.

**`response_item.payload.type`:** `message` {`role`: user / assistant / developer, `content`: [`input_text` | `output_text` | `input_image` | …], `phase`: `commentary` / `final_answer`}; `function_call` {`name`, `arguments` — a JSON *string*, `call_id`}; `function_call_output` {`call_id`, `output` — text or content items, no structured success flag; command runs end with `Process exited with code N`}; `custom_tool_call` (+ output); `local_shell_call` {`action.command`: string array}; `reasoning`; `web_search_call`; `tool_search_call`; `agent_message`; `compaction`; unknown types are `other`. Some items carry `encrypted_content`.

**`event_msg`:** `turn_aborted` {`reason`: interrupted / replaced / review_ended / budget_limited} marks an interruption; `thread_rolled_back` a rollback (fields not yet checked).

**What counts as conversation** — copied from Codex's own memory pipeline (`codex-rs/memories/write/src/rollout_input.rs`, `codex-rs/rollout/src/policy.rs`):

- Only `response_item` and `inter_agent_communication` records; `developer` messages, `reasoning`, compaction, `event_msg` and `turn_context` are not conversation.
- From user messages remove fragments wrapped in `# AGENTS.md instructions … </INSTRUCTIONS>` and `<skill> … </skill>`.
- A user message containing `<environment_context>`, or whose metadata `content_item_kinds` are all non-`user.*`, is harness context, not the user.
- `<subagent_notification>` or a `Message Type: / Task name: / Sender: / Payload:` header is another agent talking.
- The answer to a `request_user_input` tool call *is* the user speaking.
- Only interactive sources are used: `cli`, `vscode`, custom `atlas` / `chatgpt`. Exec, MCP, subagent and internal threads (including Codex's own memory consolidation) are skipped. Optionally, threads that used web or tool search are marked "polluted" and excluded.

## Claude Code

Closed source. Observed on the record structure (keys and counts only) of real Claude Code 2.x transcripts (18 files, 2026-10-30):

- `~/.claude/projects/<encoded cwd>/<sessionId>.jsonl`. No header line: every record carries `sessionId`, `cwd`, `gitBranch`, `version`, `timestamp`.
- Records form a tree through `uuid` / `parentUuid`; `last-prompt` records carry `leafUuid`; `isSidechain` marks subagent records.
- Subagent transcripts: `<encoded cwd>/<sessionId>/subagents/agent-<agentId>.jsonl`, with a sibling `agent-*.meta.json`. The parent is the `<sessionId>.jsonl` next to the directory. Sidechain records inside a main transcript were not seen.
- One API response is split into several `assistant` records, one per content block (`text`, `thinking`, `tool_use`), sharing `message.id` and differing in `apiBlockIndex`.
- Tool results are `user` records holding `tool_result` blocks (plus a structured `toolUseResult`) — not the user speaking. Also not the user: `user` records with `isMeta`, `attachment` records (system reminders, hook context), `system` records.
- Local slash commands are `user` records whose `content` is a string of wrapper tags, with no `isMeta`: `<command-name>/model</command-name>`, `<command-message>model</command-message>`, `<command-args>jd/claude-opus-4.8</command-args>`. The output follows as another `user` record: `<local-command-stdout>Set model to Opus 4 …</local-command-stdout>`.
- A user interrupt is a `user` record whose text is `[Request interrupted by user]` or `[Request interrupted by user for tool use]` (sometimes with `interruptedMessageId`).
- Rendering: slash commands become `[user ran …]` (`/clear` becomes the context-reset note and starts a turn), command output becomes `  [command output: …]`, interrupts become `  [assistant turn aborted by the user]`.
- Bookkeeping: `mode`, `cost-state`, `tools-used`, `queue-operation`, `atis-latch`.
- Claude Code deletes transcripts older than `cleanupPeriodDays`, so older sessions cannot be searched.
- Generate fixtures with `claude -p` in a temporary `HOME`.

## Gemini CLI

From the source of `google-gemini/gemini-cli` (`packages/core/src/services/chatRecordingService.ts`, `chatRecordingTypes.ts`; main on 2026-10-28). Checked against sessions Gemini CLI 0.66.0 wrote (`test/fixtures/gemini`, regenerated by `gen.sh` against a scripted mock model).

- `~/.gemini/tmp/<project id>/chats/session-<YYYY-MM-DDTHH-MM>-<id8>.jsonl` (`GEMINI_CLI_HOME` replaces `~`). `<project id>` is a short slug from `~/.gemini/projects.json` (older versions: the sha256 of the project root); the directory holds `.project_root` with the real path, which is the session's cwd.
- Subagents: `chats/<parent session id>/<subagent session id>.jsonl`, metadata `kind: "subagent"`, with the workspace `directories`.
- JSONL, append-only. Lines: a metadata record `{sessionId, projectHash, startTime, lastUpdated, kind?, directories?, summary?}`; message records `{id, timestamp, type: user | gemini | info | error | warning, content, …}` (`gemini` messages carry `toolCalls[{id, name, args, result, status}]`, `thoughts`, `tokens`, `model`); `{$set: {…}}` metadata updates; `{$patch: {id?, content?, toolCalls?, updates?, removeIds?, orderIds?}}`; `{$rewindTo: <message id>}`.
- The conversation is the replay of all lines: a message line with a known id replaces that message in place; `$patch` fills in tool results that arrive late and can remove or reorder messages; `$rewindTo` drops the message and everything after it (unknown id: everything).
- `content` is a GenAI `PartListUnion` (string, part or parts); tool results are `functionResponse` parts with `response.output` or `response.error`. Tool call `status`: validating, scheduled, executing, awaiting_approval, success, error, cancelled.
- Legacy sessions: one `session-*.json` holding a whole `ConversationRecord {…, messages: […]}`.
- Not the user speaking: prompts starting with `/` (slash commands) or `?`, `<session_context>` and `<hook_context>` messages. `info` and `warning` messages belong to the CLI.
- Seen in the real files: a `gemini` message is written again under the same id when its tool calls get results; each tool reply is also a separate `user` message of `functionResponse` parts (the result is already on the tool call, so it is not rendered twice); the first user message is the CLI's `<session_context>`; `.project_root` holds the real working directory; the shell tool wraps its report in `<untrusted_context>` and a failing command still has status `success` with an `Exit Code: N` line; a subagent file's first user message is its delegated task, the later ones are the loop's nudges.
- Not produced by a scripted run, so covered only on small records: `$patch`, `$rewindTo`, `$set` with messages, legacy `.json`.
- Seen with a real model (DeepSeek, through `test/fixtures/gen/gemini-to-openai.mjs`): after a parallel batch of tool calls, `$patch` stores the *whole batch's* `functionResponse` parts in the `result` of every call, so a call's answer is picked by call id, then by tool name (`geminiOwnResult`); the model often pipes `go test` through `tail`, which hides the exit code (status `success`, `Exit Code: 0`), so a failing run is only visible in its text.
- Fixtures: `test/fixtures/gemini/gen.sh` runs the CLI against `test/fixtures/gen/mock-model.mjs` in a temporary `HOME` (settings: API-key auth, folder trust off; `GOOGLE_GEMINI_BASE_URL` points at the mock); `test/fixtures/real/gen.sh gemini` does so against a real model.

## Qwen Code

From the source of `QwenLM/qwen-code` (`packages/core/src/services/chatRecordingService.ts`, `agents/agent-transcript.ts`; main on 2026-10-28). Checked against sessions Qwen Code 0.26.3 wrote (`test/fixtures/qwen`, regenerated by `gen.sh` against a scripted mock model).

- `~/.qwen/projects/<cwd with every non-alphanumeric character replaced by "-">/chats/<sessionId>.jsonl` (`<sessionId>.runtime.json` beside it is a live-status sidecar). Subagents: `<project dir>/subagents/<parent sessionId>/agent-<id>.jsonl` with `isSidechain` records, and `agent-<id>.meta.json` (`agentType`, `description`, …).
- JSONL, append-only. Every record is a `ChatRecord {uuid, parentUuid, sessionId, timestamp, type, cwd, version, gitBranch?, message?, model?, usageMetadata?, toolCallResult?, subtype?, systemPayload?, provenance?, …}`: a tree like Claude Code's, but `message` is a GenAI `Content {role, parts[]}`.
- `type: user` (parts: text), `assistant` (text, `{text, thought: true}`, `{functionCall: {id, name, args}}`), `tool_result` (`{functionResponse: {id, name, response: {output | error}}}` plus `toolCallResult.status`), `system` (bookkeeping: `slash_command`, `chat_compression`, `ui_telemetry`, `custom_title` with `systemPayload.customTitle`, `rewind`, `notification`, …).
- A `user` record with a subtype other than `mid_turn_user_message` (notification, goal_runtime, agent_message, …) was written by the CLI or a workspace agent. `mid_turn_user_message` is a follow-up the user typed while the agent worked.
- Sniffing: Qwen and Claude Code records share `uuid`/`parentUuid`/`sessionId`/`cwd`; Qwen's `message.parts`, `tool_result` records, `systemPayload` and `provenance` tell them apart. Gaps: `rewind` and `chat_compression` are not applied, records are rendered in file order.
- Seen in the real files: user records have `provenance: "real_user"`; `ui_telemetry`, `attribution_snapshot` and `memory_catalog_snapshot` system records follow each turn; the shell tool reports `Command: … Directory: … Output: … Error: … Exit Code: N Signal: …`, and a failing command is a `response.error` with `toolCallResult.status: "error"`; a relative path given to `read_file` is refused as an error result. A headless 0.26.3 run offers no subagent tool (tools: edit, glob, grep_search, notebook_edit, read_file, run_shell_command, skill, tool_call, tool_search, write_file), so the `subagents/` layout above comes from the source only.
- Seen with a real model (DeepSeek): parallel tool calls are recorded as the assistant record's call parts followed by the results, which renders as calls first, then results; "file not read yet" edit refusals arrive as error results; no thought parts are written for this model.
- Fixtures: `test/fixtures/qwen/gen.sh` runs the CLI against `test/fixtures/gen/mock-model.mjs` (OpenAI-compatible, via `OPENAI_BASE_URL`) in a temporary `HOME`; `test/fixtures/real/gen.sh qwen` does so against a real model.

## opencode

From the source of `sst/opencode` at release v1.19.5 (`packages/core/src/session/sql.ts`, `packages/schema/src/v1/session.ts`, `packages/core/src/database/database.ts`). Checked against a database opencode-ai 1.19.5 wrote (`test/fixtures/opencode/opencode.db`, regenerated by `gen.sh` against a scripted mock model). The main branch has begun a `session_v2` / `session_message` schema, which is not read.

- One SQLite database in WAL mode: `$XDG_DATA_HOME/opencode/opencode.db` (`~/.local/share/opencode`); dev channels use `opencode-<channel>.db`. Opened read-only.
- Tables: `session` (`id`, `project_id`, `parent_id`, `directory`, `title`, `time_created`, `time_updated` in ms, …), `message` (`id`, `session_id`, `time_created`, `data` JSON), `part` (`id`, `message_id`, `session_id`, `data` JSON). Ids ascend with time (`ses_…`, `msg_…`, `prt_…`). A `parent_id` marks a subagent session (the task tool).
- Message `data`: `{role: "user" | "assistant", time: {created, completed?}, …}`; assistant adds `error?` (`{name, data: {message}}`, `MessageAbortedError` for interrupts), `summary?` (a compaction summary), `path: {cwd, root}`, `parentID`, `modelID`, `tokens`.
- Part `data` (no ids): `text {text, synthetic?, ignored?}`, `reasoning`, `tool {callID, tool, state: {status: pending | running | completed | error, input, output | error}}`, `file {mime, filename, url}`, `subtask`, `agent`, `compaction`, `step-start`, `step-finish`, `snapshot`, `patch`, `retry`.
- Not the user speaking: `synthetic` and `ignored` text (injected context, results of `@file` mentions). Not rendered: reasoning, step and snapshot parts, compaction summaries.
- A session is not a file. The adapter builds one JSON-lines stream per session (`ReadRaw`: a `session` line, then a `message` line per message with its parts) and parses that; offsets are offsets in the stream, `SourceFile.Inner` is the session id, `Key` is `<db>#<session id>`, and the size of the stream is the session's size. A tool part that completes after its message was read shows up on the next call.
- Seen in the real database: the tables and columns are as above; a prompt given to `opencode run` is stored wrapped in double quotes; the bash tool finishes `completed` whatever the command did, its exit code is in `state.metadata.exit`; subagent sessions have `parent_id` and a title ending in `(@general subagent)`; `--continue` appends to the same session. Not produced by a scripted run: `error` tool states, aborts, attachments, compaction summaries (covered on a hand-built database).
- Seen with a real model (DeepSeek): the same shapes as with the scripted run; the failing `go test` shows as `✗` through `metadata.exit`, and edits refused because the file was not read first are `error` tool states.
- Fixtures: `test/fixtures/real/gen.sh opencode` does the same against a real model; `test/fixtures/opencode/gen.sh` runs `opencode run` against `test/fixtures/gen/mock-model.mjs` in a throwaway `HOME` / `XDG_*` tree (`OPENCODE_DISABLE_MODELS_FETCH=1`; a start-up stall now and then is retried).

## Adding an agent

1. Read the agent's source (or real files) and write the facts here, with references.
2. Generate a fixture with the agent itself under `test/fixtures/<agent>/`: write a `gen.sh` like the ones for gemini, qwen and opencode (throwaway `HOME`, `test/fixtures/gen/mock-model.mjs` as the model — extend its scenarios if the agent needs another protocol), then compare the real files with what you read in the source and fix the adapter.
3. (Sessions inside a database: implement `sources.RawReader`, `Container` and set `SourceFile.Inner`, as `opencode.go` does.) Implement `sources.Adapter` in `internal/sources/<agent>.go` and register it in `sources.All` (order matters for sniffing: more specific formats first); add the kind to `ir` and its default directories to `config.DefaultDirs` (the `MG_<AGENT>_DIRS` variable then exists for free).
   - Text the renderer writes itself goes into `sources.Synthetic` (mg skips unread files and records based on it).
   - mg's byte prefilter assumes the agent writes non-ASCII text as UTF-8, not `\uXXXX` escapes (true for the JavaScript and Go agents here). An agent that escapes (Python's `json.dumps` default) needs that handled before mg may skip files for non-ASCII terms.
4. Mirror the omp tests: rendering, incremental offsets, a partially written last line, subagents, skipped sessions.
5. Only then enable it by default.
